# USB Project — Line-by-Line Walkthrough
## Phase 2: Buffering & FIFOs (`usb_bus_smoother.vhd` + `usb_ip_fifo.vhd`)

> Builds directly on Phase 1. The RTL patterns (clocked process, FSM,
> reset, signal-vs-variable, active/valid/data interface) are assumed known —
> we only slow down on the *new* ideas: FIFOs, clock-domain crossing, and
> concurrent (outside-the-process) logic.

### First: a correction to earlier explanations

In my earlier summaries I described this block as a "ping-pong double
buffer." **That was wrong.** Reading the actual code, it's a **single FIFO
with a small drain-controlling state machine.** No ping-pong, no double
buffer. I'm flagging it so you don't walk into an interview with the wrong
mental model — the real design is simpler than I'd claimed.

---

## The one-line interview answer

> "`usb_bus_smoother` absorbs bursty USB traffic into a FIFO and releases it
> as a clean, gap-controlled stream to the downstream logic. USB data arrives
> in bursts with idle gaps; the modules after it want a predictable flow. The
> FIFO decouples the two, and a small state machine decides *when* to start
> draining it."

# Part A — `usb_ip_fifo.vhd` (the building block)

This file is **auto-generated by Intel's Quartus wizard** — you did not hand-
write it, and in an interview you should say exactly that. Lines 1–18 are the
generator's banner; line 15 literally says "DO NOT EDIT THIS FILE."

**What it is (line 4, 9):** a `dcfifo` — a **d**ual-**c**lock FIFO. A FIFO is a
first-in-first-out queue (like a checkout line: first byte in is first byte
out). "Dual-clock" means it's *designed* to safely move data between two
independent clock domains.

**Its configuration (lines 106–118) — the numbers that matter:**
```vhdl
intended_device_family => "Cyclone 10 LP",   -- which FPGA chip
lpm_numwords => 1024,                          -- holds 1024 entries
lpm_width => 16,                               -- each entry is 16 bits wide
lpm_widthu => 10,                              -- 10-bit address (2^10 = 1024)
rdsync_delaypipe => 4,                         -- 4-stage synchronizer, read side
wrsync_delaypipe => 4                          -- 4-stage synchronizer, write side
```
- **1024 × 16:** capacity is 1024 slots, 16 bits each.
- **`rdsync_delaypipe => 4` / `wrsync_delaypipe => 4`** — this is the important
  one for interviews. A dual-clock FIFO safely crosses clock domains using a
  **synchronizer** — a chain of flip-flops that lets a signal settle before the
  other clock reads it. 4 stages = very safe against **metastability** (the
  hazard when a signal changes right as a flip-flop samples it). **If asked
  "how do you cross clock domains safely?" →** "a dual-clock FIFO with a multi-
  stage synchronizer on the read/write pointers — this one uses 4 stages."

**The key irony (you must know this):** this FIFO is *capable* of dual-clock
operation, but Part B wires **both its clocks to the same signal.** So its
domain-crossing ability goes **unused** in this design. More on that below.

# Part B — `usb_bus_smoother.vhd` (the logic around the FIFO)

## Entity (lines 11–33)
Same active/valid/data streaming interface from Phase 1, but now with **five**
signals per side instead of three:
```vhdl
hie_rxactive  -- packet in progress
hie_rxvalid   -- this byte is valid
hie_rxerror   -- NEW: the PHY flagged a receive error on this packet
hie_rxdata    -- the 8 data bits
hie_rxeop     -- NEW: end-of-packet marker
```
- **`rxerror` and `rxeop`** are the two extra USB stream signals. Note them —
  they matter for a limitation we'll hit later (spoiler: they get dropped
  further down the pipeline).

## Declarations (lines 38–54)
```vhdl
CONSTANT DATA_WIDTH_FIFO : natural := 16 ;     -- FIFO is 16 bits wide
SIGNAL wr_en_1     : std_logic;                 -- "write into FIFO now"
SIGNAL wr_data_1   : std_logic_vector(15 downto 0); -- the 16-bit word we write
SIGNAL rd_en_1     : std_logic;                 -- "read from FIFO now"
SIGNAL fifo_empty_1: std_logic;                 -- FIFO says "I'm empty"
signal rd_data_1   : ...(15 downto 0);          -- word we present downstream
signal rd_data_s1  : ...(15 downto 0);          -- raw word straight off the FIFO
signal wrusedw1    : ...(9 downto 0);           -- how full the FIFO is (word count)
signal state_smoother: ...(2 downto 0);         -- the drain FSM's state
signal waitcnt     : ...(2 downto 0);           -- a small delay counter
```
Notice: **8 bits of data become a 16-bit FIFO word.** Why 16 for 8 bits of
data? Because the smoother packs the *control* signals in alongside the data —
see the next part.

## Concurrent logic (lines 76–89) — runs continuously, outside any process

```vhdl
wr_en_1   <=  hie_rxvalid or rxactive_fall;
```
- **Write into the FIFO** whenever a byte is valid **OR** when `active` just
  fell (the falling edge — end of packet). The second term makes sure the
  end-of-packet event itself gets stored, not just the data bytes.

```vhdl
wr_data_1 <= x"0" & hie_rxactive & hie_rxvalid & hie_rxerror & hie_rxeop & hie_rxdata;
```
- **This is the clever line.** It builds the 16-bit FIFO word by
  **concatenating** (`&`) the control bits *in front of* the 8 data bits:
  `[0000][active][valid][error][eop][8-bit data]` = 4+1+1+1+1+8 = 16 bits.
- **Why?** So the four status signals travel *through the FIFO alongside their
  data byte* and stay perfectly aligned. When the byte comes out the other
  side, its active/valid/error/eop come out with it, same clock. Clean trick —
  worth calling out in an interview as "I packed the sideband signals into the
  FIFO word so they can't desynchronize from the data."

```vhdl
rd_en_1   <=  (not fifo_empty_1) and rd_en_sm;
```
- **Read from the FIFO** only when it's **not empty** AND the state machine says
  "drain now" (`rd_en_sm`). This is how the FSM controls the *timing* of the
  output stream.

```vhdl
hie_rxactive_dism <= rd_data_1(11);   -- unpack the word back into separate signals
hie_rxvalid_dism  <= rd_data_1(10);
hie_rxerror_dism  <= rd_data_1(9);
hie_rxeop_dism    <= rd_data_1(8);
hie_rxdata_dism   <= rd_data_1(7 downto 0);
```
- The mirror of the packing line: split the 16-bit word back into the five
  output signals. Bit 11 = active, bit 10 = valid, etc. (Count the bit
  positions against the packing order above — they line up.)

## Process 1 — falling-edge detector (lines 92–104)
```vhdl
process(usb_clk_us)
begin
    if(rising_edge(usb_clk_us)) then
        if(core_reset_n = '0') then
            s_rxactive <= '0';
        else
            s_rxactive <= hie_rxactive;   -- remember what active was LAST cycle
        end if;
    end if;
end process;

rxactive_fall <= '1' when (hie_rxactive = '0' and s_rxactive = '1') else '0';
```
- **The universal edge-detector pattern.** `s_rxactive` is a one-cycle-delayed
  copy of `hie_rxactive`. Then `rxactive_fall` is true exactly when active
  *was* 1 last cycle and *is* 0 now — i.e., the moment the packet ended.
- **Interview classic:** "how do you detect an edge in RTL?" → "register the
  signal one cycle, then compare old vs new. Old=1, new=0 is a falling edge."
  Memorize this; it comes up constantly.

## Process 2 — the drain-control FSM (lines 107–160)
This decides *when* to start emptying the FIFO. Defaults first (Phase 1
pattern): `rd_en_sm <= '0'`, `rd_data_1 <= 0`, `waitcnt <= 0` each cycle.

```vhdl
when "000" =>                              -- IDLE: wait for a packet to begin
    if(hie_rxvalid = '1') then
        state_smoother <= "001";
    end if;
```
- State 0: sit until the first valid byte arrives, then advance. (Data is
  already being written to the FIFO by the concurrent logic — the FSM only
  controls *reading*.)

```vhdl
when "001" =>                              -- FILLING: wait for enough data
    if(hie_rxactive = '0') then            -- packet ended → safe to drain
        state_smoother <= "010";
    elsif(wrusedw1 = 86) then              -- OR the FIFO hit 86 words → drain anyway
        state_smoother <= "010";
    end if;
```
- State 1: the heart of the "smoothing." It waits until **either** the packet
  finishes **or** the FIFO has accumulated 86 words. This head-start (buffering
  up before draining) is what smooths the gaps — by the time we start reading,
  there's enough cushion that the output won't underrun.
- **`wrusedw1 = 86`** — the "86" is a hand-tuned threshold. In an interview,
  frame it honestly: "a magic number tuned to the packet sizes; I'd parameterize
  it in production."

```vhdl
when "010" =>                              -- SETTLE: brief fixed delay
    waitcnt <= waitcnt + 1;
    if(waitcnt = "010") then               -- after 2 cycles
        rd_en_sm       <= '1';             -- start draining
        state_smoother <= "011";
    end if;
```
- State 2: a tiny 2-cycle pause "to handle 1-byte packets" (the code comment,
  line 136). Edge-case padding so even a minimal packet drains cleanly.

```vhdl
when "011" =>                              -- DRAINING
    rd_en_sm <= '1';
    if(fifo_empty_1 = '1') then            -- FIFO drained
        state_smoother <= "100";
        rd_data_1 <= x"0800";              -- force active=1 for one last cycle (bit 11)
    else
        rd_data_1 <= rd_data_s1;           -- pass FIFO output through
    end if;
```
- State 3: actively read the FIFO, passing each word through to the output.
  When empty, it manually drives one final word `0x0800` — that's bit 11 set,
  i.e. `active=1` with everything else 0 — to hold `active` high one extra
  cycle for clean end-of-packet timing (same timing-hygiene idea as the
  `pkt_txcrc2` tail in Phase 1).

```vhdl
when "100" =>  state_smoother <= "000";    -- done, back to idle
when others => state_smoother <= "000";    -- safe recovery
```

## FIFO instantiation (lines 165–182)
```vhdl
usb2_sync_fifo_rx_hie : usb_ip_fifo
PORT MAP (
    aclr    => '0',
    wrclk   => usb_clk_us,      -- WRITE clock
    rdclk   => usb_clk_us,      -- READ clock  ← SAME SIGNAL
    wrreq   => wr_en_1,
    rdreq   => rd_en_1,
    wrfull  => open,            -- "open" = we don't use this output
    rdempty => fifo_empty_1,
    wrusedw => wrusedw1,
    data    => wr_data_1,
    q       => rd_data_s1
);
```
- **`wrclk` and `rdclk` are both `usb_clk_us`** (lines 170–171). This is the
  irony flagged in Part A: a dual-clock FIFO wired as single-clock. Here it's
  used purely as **elastic buffering**, not domain-crossing.
- **`wrfull => open`** — `open` means "leave this output disconnected." The
  design never checks if the FIFO is full, relying on it being big enough
  (1024 words) that it never overflows in practice. *Interview-worthy risk:*
  "there's no full-detection/backpressure — it assumes the FIFO can't overflow.
  In a hardened design I'd wire `wrfull` and handle it."
- **`usb2_sync_fifo_rx_hie`** is just the instance *name* — note it's
  confusingly similar to the unrelated dead file `usb2_sync_fifo_rx.v`, which
  is NOT this component. Don't conflate them.

## Phase 2 summary (say this)
> "It packs each data byte plus its four sideband signals into one 16-bit FIFO
> word so they stay aligned, writes every valid byte in, and a 5-state FSM
> waits until the packet ends or the FIFO reaches 86 words before draining — a
> buffer head-start that smooths USB's bursty timing. It uses a dual-clock FIFO
> but ties both clocks together, so here it's pure elastic buffering, not a
> clock crossing."

## New patterns learned this phase
1. **FIFO** — first-in-first-out queue for decoupling producer/consumer rates.
2. **Dual-clock FIFO + synchronizer pipeline** — the standard safe CDC method.
3. **Packing sideband signals into the data word** so they can't desync.
4. **Edge detection** (register-and-compare).
5. **`open`** on an unused port; **concatenation (`&`)** to build wide words.
6. **Threshold-based draining** as a smoothing technique.
